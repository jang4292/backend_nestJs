NestJS Backend API

Last updated: 2026-11-09 · develop 9b731ef + chore/project-audit-2026-11 · Documentation index (Korean): docs/README.md

A NestJS 11 backend that provides local JWT authentication, user profiles, and music catalog and playlist APIs. It runs on MariaDB through TypeORM. Settings are validated at startup, and the schema changes only through versioned migrations.

#Features

  • Local registration and JWT login (HS256). A password change requires currentPassword.
  • Minimal RBAC: music write APIs are admin-only (users.role).
  • Music catalog (tracks, audio assets, playlists) and legacy music APIs.
  • Social login modules for Google, Apple, Kakao, Naver and Facebook. They are currently all disabled; only local login is used. Each provider is opt-in, see SNS login.
  • Helmet, an explicit CORS allow-list, throttling, DTO validation and a single error envelope.
  • Per-environment env files, read-only DB checks, and migrations verified on MariaDB in CI.

#Quick start (Local)

Requires Node.js 24 (.nvmrc; engines requires >= 22.13). Local means the app runs on your PC and connects to the shared dev MariaDB server, using a database dedicated to this app (app_db_dev).

npm ci
cp .env.example .env && chmod 600 .env
# edit .env: DB_HOST, DB_PORT, DB_USERNAME, DB_PASSWORD, DB_DATABASE=app_db_dev
npm run db:check     # read-only: connection, TLS, privileges, ownership, pending migrations
npm run db:setup     # create the database if missing, then apply migrations (tables)
npm run start:dev    # http://localhost:3000, Swagger at /api-docs
  • Type the password into the DB_PASSWORD= line of .env yourself. The file is ignored by git; do not put the password in chats, docs or commits.
  • Each command reads one file: db:check, db:setup, migration:* and start:dev read .env; the :test commands and test:e2e read .env.test.local; the :prod commands read .env.production. When a value is missing, the error names the file it read and hints if another env file has that key.
  • db:check also reports whether the account has the privileges migrations need (SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX) and prints the exact GRANT for anything missing. db:setup stops before changing anything when privileges are missing.
  • Other databases on the server are never touched. db:setup and db:reset:test only work on a database that contains nothing but this app's tables (APP_TABLES); otherwise they refuse and change nothing. Grant the app account privileges on its own databases only, never ON *.*.
  • Database names may use letters, digits, _ and -.
  • db:setup is safe to run again: it never recreates an existing database and never re-runs an applied migration.
  • The dev MariaDB server has no TLS (db:check prints tls: off). Restrict its port to developer IPs, or connect through an SSH tunnel.

#Environments

One env file per environment, chosen by NODE_ENV (see src/config/env-files.ts). The app, the migration CLI, the db:* tools and e2e all use the same rule.

  • Exported shell variables override file values.
  • ENV_FILE=<path> replaces the file choice.
Environment NODE_ENV File (git-ignored) Template Database
Local development (default) .env .env.example dev server, dedicated app_db_dev
Test (e2e, inside Local) test .env.test.local (required) .env.test.example dev server, dedicated app_db_test (*_test only)
Prod production .env.production .env.production.example EC2 localhost MariaDB

Validation rules (startup, env:check, db:*):

  • Always required: DB_USERNAME, DB_PASSWORD, DB_DATABASE, JWT_SECRET. JWT_EXPIRES_IN must look like 3600, 30m, 1h or 7d. CORS_ORIGIN must not be *.
  • Always rejected: DB_SYNCHRONIZE=true. Synchronize can drop columns and their data, so the schema changes only through migrations.
  • NODE_ENV=test: only accepts *_test databases.
  • NODE_ENV=production also requires:
    • CORS_ORIGIN: an origin list, or none to disable CORS
    • JWT_SECRET: at least 32 characters, with no placeholder text
  • New keys: add them to src/config/app-env.ts and to scripts/runtime-env-keys.cjs. A spec fails when the two lists drift.

Full guide with account SQL and common errors: docs/deployment/database-environments.kr.md.

#Database and migrations

  • Tables come only from migrations (src/database/migrations/). Never use synchronize (rejected at startup) or hand-written CREATE TABLE.
  • The same migration files go through every environment in order: CI (empty DB) → Test → Local → Prod.
  • Migrations are an explicit deploy step. The app does not run them on startup. It logs a warning, or an error in production, when migrations are pending.
  • Database containers are created once per environment. Local and Test use db:setup. Prod uses admin SQL, so the app account holds privileges on its own database only.
  • The app only ever changes its own database. Every write checks privileges and ownership first and changes nothing if either fails.
  • Back up before any production migration. Some legacy migrations cannot be reverted.

Why it works this way (manual SQL vs a command vs auto-run, verification layers, rollback): docs/learning/database-schema-management.kr.md.

#Deploy (EC2 + PM2)

git pull --ff-only
npm ci
npm run build
npm run env:check:prod       # validate .env.production without touching the DB
npm run db:check:prod        # read-only: connection, privileges, pending migrations
# back up the database when migrations are pending (mysqldump --single-transaction)
npm run migration:run:prod
npm run pm2:reload           # ecosystem.config.cjs pins cwd and NODE_ENV=production
curl -fsS http://127.0.0.1:${PORT:-3000}/health   # 503 when the DB is down
  • After 1765000000000-AddRoleToUsers: grant admin manually with UPDATE users SET role = 'admin' WHERE username = '<admin-username>';.
  • 1766000000000-AddSessionVersionToUsers adds users.sessionVersion. A password change now revokes every earlier token. To roll the column back, redeploy the previous build first, then run migration:revert:prod.
  • Keep database dumps outside the repository (umask 077); *.sql and *.sql.gz are git-ignored.
  • Optional AWS Secrets Manager: run eval "$(AWS_SECRET_ID=<id> AWS_REGION=ap-northeast-2 npm run -s secrets:export)" first. Exported values override .env.production.
  • Full checklist, rollback and TLS: docs/deployment/mariadb-systemd.kr.md.

#SNS login

All providers are off: AUTH_<PROVIDER>_ENABLED=false, where <PROVIDER> is GOOGLE, APPLE, KAKAO, NAVER or FACEBOOK.

  • A disabled provider needs no settings, and its routes return 503 AUTH_<PROVIDER>_DISABLED.
  • Naver access-token login stays blocked even when Naver is enabled (AUTH_NAVER_ACCESS_TOKEN_LOGIN_ENABLED=false).

Before enabling a provider, complete docs/auth/sns-reenable-checklist.kr.md.

#Verification and CI

npm run lint:check && npm run format:check && npm run typecheck && npx jest && npm run build
npm run db:setup:test && npm run test:e2e      # needs .env.test.local

GitHub Actions (.github/workflows/ci.yml) runs on every pull request and on every push to develop and main:

  • verify: lint, format, typecheck, unit tests, build, a critical production npm audit, and a link/anchor check of every Markdown document (npm run docs:html:verify).
  • database (MariaDB 10.11 service container):
    1. apply every migration to an empty database
    2. assert that nothing is pending
    3. revert and re-apply the latest migration
    4. run the schema drift check (report-only for now, audit item DB-12)
    5. run e2e
