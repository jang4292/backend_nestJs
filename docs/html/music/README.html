Music API 운영 개선 문서

최신화 기준: 2026-11-09 · develop 9b731ef + chore/project-audit-2026-11

NestJS Music API와 EC2 내부 MariaDB 운영 개선 문서 모음입니다.

#문서 구조

  • MariaDB 운영 가이드: DB 생성, migration, backup, 배포, 보안
  • 결정 및 보류 항목: 현재 코드와 제품 정책에서 확정되지 않은 사항
  • Music API 구조 검토: 구조 문제와 단계적 개선 방향(2026-09 검토, 이후 상태 표기)
  • 남은 요구사항과 우선순위: 최신 감사 리포트 로드맵
  • 학습 가이드: 도메인, 요청 흐름, TypeORM, 공개/보호 API를 따라가는 입문 문서
  • 설계 및 아키텍처: Legacy/Catalog 구조, 데이터 관계, API 경계와 향후 방향
  • 원인 분석 및 트러블슈팅: route, migration, relation, 공개 URL 문제 분석
  • 체크리스트: 학습, 기능 개발, DB, 음원 보안, 배포, 장애 대응 점검표

#현재 구현 원칙

  • synchronize=true는 어떤 환경에서도 사용하지 않습니다(기동 거부). 스키마는 Migration으로만 바꿉니다.
  • 애플리케이션 시작 시 DB 생성이나 migration을 자동 실행하지 않습니다.
  • 기존 migration 파일은 수정하지 않고, 새로운 schema 변경은 새 migration으로 추가합니다.
  • Playlist 날짜 중복과 Playlist 내 Track 중복 정책은 확정 전까지 DB 제약으로 강제하지 않습니다.
  • Active catalog는 Track 1:N AudioAsset 관계이며, 실제 S3 업로드 구현은 별도 작업입니다.
  • Track.bpm은 카탈로그 BPM, AudioAsset.bpm은 파일/분석 BPM으로 분리하며 자동 동기화하지 않습니다.
  • 기존 Artist/Track/Playlist API는 /music/legacy에 보관하고, 새 catalog API는 /music을 사용합니다.
  • Catalog Playlist는 draft/published/archived 상태를 사용하며 공개 API는 published만 반환합니다.
  • Catalog Playlist item은 position으로 정렬하고 (playlistId, position) unique 제약을 사용합니다.
  • 공개 응답에는 음원 URL과 내부 storage 정보가 포함되지 않습니다. playback/presigned URL은 후속 작업입니다.
  • Catalog와 Legacy의 모든 쓰기 API는 admin 전용(@AdminOnly())입니다. 공개 조회(/music/tracks, /music/public/*, /music/legacy/tracks)는 인증이 필요 없고, 나머지 조회는 로그인이 필요합니다.
  • 삭제하려는 리소스를 다른 데이터가 참조하면(FK) 409 FOREIGN_KEY_CONSTRAINT를 반환합니다.
  • 2026-09-13 기준 개발 DB에는 Legacy archive, Catalog music, Catalog playlist Migration이 적용되어 있었습니다. 1765000000000-AddRoleToUsers를 포함한 환경별 상태는 migration:show로 확인합니다.
