#3.1 인증·세션

ID 등급 발견 사항 조치
SEC-17 High ProviderReadinessGuard가 요청 경로를 대소문자 구분 정규식(^/auth/([^/]+))으로 검사했습니다. Express 라우팅은 대소문자를 구분하지 않아 /auth/GOOGLE/*, /auth/Kakao/*가 가드를 통과해 컨트롤러에 도달합니다. 꺼진 provider는 설정이 비어 있어, 검증이 다음처럼 fail-open이었습니다.
· Google: audience: undefined → 다른 OAuth client용 ID Token도 통과
· Apple: audience: undefined
· Kakao: KAKAO_APP_ID가 없으면 경고 후 app_id 검증 생략
결과적으로 "SNS 비활성" 상태에서도 다른 앱에서 발급된 토큰으로 <provider>_<sub> 계정이 생기고 세션 JWT가 발급됩니다. verify-id-token은 공개 검증기로 동작합니다		 ✅ 가드가 경로 대신 @SocialProviderRoute() 메타데이터로 판정합니다(src/common/auth/social-provider-route.decorator.ts). 5개 컨트롤러에 메타데이터가 빠지면 spec이 실패합니다
✅ fail-closed: Google·Apple은 audience가 비면 *_CONFIG_MISSING(503)을 반환합니다. Kakao는 KAKAO_APP_ID가 없으면 거부하며, Kakao가 켜져 있으면 모든 환경에서 필수입니다
✅ e2e에 /auth/GOOGLE/login, /auth/Kakao/login 503 확인 추가
AUTH-3 Medium (11-08 감사에서 로드맵) 비밀번호를 바꿔도 기존 JWT가 만료까지 유효했습니다. 토큰이 탈취되면 비밀번호를 바꿔도 막을 수 없습니다 ✅ users.sessionVersion(migration 1766)을 추가했습니다. JWT에 sv를 넣고 JwtStrategy가 매 요청 DB 값과 비교합니다. 비밀번호를 바꾸면 버전이 1 오릅니다. 배포 전에 발급된 토큰은 sv가 없어 0으로 간주하므로 배포 직후에도 유효합니다
SEC-19 Medium 로그인 제한이 IP당 5회/분뿐이었습니다. IP를 바꾸며 한 계정을 공격하는 무차별 대입을 막지 못합니다 ✅ 정규화한 식별자(username:alice)마다 실패 10회/15분이면 비밀번호를 검사하기 전에 429 RATE_LIMITED와 Retry-After를 반환합니다. 성공하면 초기화합니다. 없는 계정도 같은 방식으로 세어 계정 존재가 드러나지 않습니다. 저장소는 프로세스 메모리(상한 1만 키)이며 PM2 단일 인스턴스 기준입니다
SEC-18 Medium 계정 DTO에 길이 상한이 없었습니다.
· bcrypt는 72바이트 이후를 무시하므로 앞 72바이트가 같으면 같은 비밀번호로 취급

· 최소 비밀번호 길이 6자		 ✅ 새 비밀번호 8자 이상·UTF-8 72바이트 이하, username 4~50, email 255, name 100(src/users/domain/user-input-policy.ts)

SEC-16 Low (11-08 로드맵) redirect URI 허용 목록이 비면 검사를 생략했습니다 ✅ 5개 provider 모두 목록이 비면 code flow를 거부합니다(*_CONFIG_MISSING)

#3.4 SNS 설정 규칙 (재활성화 조건)

SEC-17 수정으로 provider를 다시 켤 때의 조건이 강해졌습니다. 지금은 모든 provider가 꺼져 있어 런타임 영향은 없습니다. 자세한 내용은 SNS 재활성화 체크리스트를 봅니다.

provider 새로 필수가 된 것
Google GOOGLE_ALLOWED_AUDIENCES(기동 검증은 기존과 같고, 비어 있으면 런타임에도 거부), code flow면 GOOGLE_OAUTH_REDIRECT_URIS
Apple code flow면 APPLE_REDIRECT_URIS

# 변경 영향 대응

11 새 비밀번호 8자 이상, UTF-8 72바이트 이하 가입·비밀번호 변경 400 클라이언트 입력 검증과 안내 문구

롤백

  • 앱만 되돌릴 때: 이전 빌드로 pm2:reload합니다. 이전 코드는 sessionVersion 컬럼을 읽지 않으므로 컬럼이 남아 있어도 동작합니다.
  • 컬럼까지 되돌릴 때: 먼저 앱을 이전 빌드로 되돌린 뒤 migration:revert:prod를 실행합니다. 새 코드는 entity가 이 컬럼을 조회하므로, 순서가 바뀌면 모든 사용자 조회가 실패합니다.
