DB·스키마 관리 학습 가이드: 생성, migration, 검증

최신화 기준: 2026-11-09 · develop 9b731ef + chore/project-audit-2026-11 실행 절차(명령 순서, SQL)는 환경별 DB·설정 가이드에 있습니다. 이 문서는 왜 그렇게 하는지를 설명합니다.

#1. 학습 목표

이 문서를 읽고 나면 다음 질문에 답할 수 있어야 합니다.

  • 데이터베이스와 테이블은 각각 누가, 언제 만드는가?
  • Test에서 동작하던 스키마가 Local이나 Prod에 없으면 어떻게 반영하는가?
  • 직접 SQL로 만들기, 명령으로 실행하기, 앱 기동 시 자동 실행하기는 무엇이 다른가?
  • 스키마 변경이 안전한지 어떤 단계에서 무엇으로 검증하는가?
  • 배포 후 문제가 생기면 어떻게 되돌리는가?
  • 같은 DB 서버에 있는 다른 DB를 어떻게 보호하는가?

#2. 용어

환경: 이 프로젝트는 세 환경으로 나눕니다(자세히는 환경별 가이드 1장).

환경 의미 DB
Local 개발 PC에서 실행(NODE_ENV=development, .env) 개발 서버의 앱 전용 DB app_db_dev
Test Local 안의 e2e(NODE_ENV=test, .env.test.local) 개발 서버의 앱 전용 DB app_db_test
Prod EC2 + PM2(NODE_ENV=production, .env.production) EC2 localhost MariaDB

데이터베이스(스키마) 테이블을 담는 이름 공간. MariaDB에서는 DATABASE와 SCHEMA가 같은 말 app_db_dev, app_db_test, 운영 DB. 앱은 자기 DB만 다룸
계정·권한 'user'@'host'와 GRANT 앱 계정은 자기 DB에만 권한
테이블·컬럼·인덱스 실제 데이터 구조 migration 파일로만 변경

앱 소유 DB 이 앱의 테이블(APP_TABLES)만 있는 DB db:setup·db:reset은 앱 소유 DB에서만 동작

핵심은 "그릇(데이터베이스·계정)"과 "내용(테이블 구조)"을 다르게 다룬다는 점입니다.

  • 그릇은 환경마다 한 번 준비하면 거의 바뀌지 않습니다. 이 일을 프로비저닝이라고 합니다.
  • 내용은 코드와 함께 계속 바뀝니다. 그래서 코드처럼 버전을 관리하는 migration으로 다룹니다.

#3. 무엇을 누가 만드나

대상 Local Test Prod
DB 서버 개발 서버 관리자 개발 서버 관리자 EC2 MariaDB 설치(1회)
데이터베이스 npm run db:setup(없으면 생성) db:setup:test / db:reset:test 관리자 SQL(1회)
계정·권한 관리자 SQL(1회) 관리자 SQL(1회) 관리자 SQL(1회), '<app>'@'localhost'
테이블·컬럼 migration:run migration:run:test migration:run:prod(배포 단계)
데이터(admin 지정 등) 필요 시 SQL 테스트가 직접 생성 배포 체크리스트의 수동 단계

Prod에서는 앱이 데이터베이스를 만들지 않습니다. db:ensure가 운영에서 거부되는 이유이기도 합니다.

  • 최소 권한 원칙: 앱 계정이 CREATE DATABASE나 DROP DATABASE를 할 수 있으면, 계정이 유출되거나 코드 실수가 있을 때 피해가 커집니다.
  • 운영 DB는 백업, 문자셋, 계정 정책과 함께 한 번에 설계합니다. 그래서 앱이 아니라 관리자가 만듭니다.

#4. 적용 방식 비교: 직접 SQL / 명령 / 기동 시 자동

직접 SQL로 생성 명령으로 migration 실행 (이 프로젝트) 앱 기동 시 자동 실행
예 콘솔에서 CREATE TABLE … npm run migration:run:prod TypeORM migrationsRun: true, Spring Boot + Flyway 기본값
재현성 낮음: 환경마다 손으로 반복하므로 빠뜨리거나 오타가 생김 높음: 같은 파일을 같은 순서로 적용 높음
이력 없음: 누가 언제 무엇을 했는지 모름 migrations 테이블과 Git 같음
실패 시 중간 상태로 남기 쉬움 배포를 멈추고 앱은 이전 버전 그대로 앱이 기동하지 못함. PM2가 재시작을 반복
여러 인스턴스 해당 없음 한 번만 실행 동시에 실행될 수 있음. TypeORM에는 실행 잠금이 없음
오래 걸리는 변경 해당 없음 별도 단계로 시간 확보 기동과 health check 지연
쓰는 곳 긴급 조치(이후 반드시 migration으로 기록) 공유 개발 DB, Prod 배포 혼자 쓰는 로컬 DB, 잠금을 지원하는 도구

정리하면 다음과 같습니다.

  • 스키마는 직접 SQL로 바꾸지 않습니다. 긴급하게 손으로 고쳤다면 같은 내용을 migration으로 남겨 다른 환경도 같은 상태가 되게 합니다.

  • 자동 실행 자체가 틀린 것은 아닙니다. Spring Boot는 기동 시 Flyway를 실행하는 것이 기본입니다. 다만 다음과 같은 이유로 이 프로젝트는 명령 방식을 택했습니다.

    • PM2 단일 프로세스에서 migration이 실패하면 서비스 전체가 재시작을 반복합니다.
    • TypeORM에는 여러 인스턴스 사이의 실행 잠금이 없습니다.
    • 공유 개발 서버의 DB가 누군가의 start:dev만으로 바뀌면 안 됩니다.

  • 업계에서 흔한 구성은 "개발 편의 명령"과 "배포용 명령"을 나누는 것입니다.

    도구 개발 편의 배포용
    Prisma migrate dev migrate deploy
    Rails db:setup db:migrate
    이 프로젝트 db:setup, db:reset:test migration:run:prod

  • 대신 앱은 기동할 때 적용되지 않은 migration이 있으면 경고만 합니다(MigrationStatusService). 자동으로 고치지는 않지만, 배포 단계를 빠뜨렸다는 것은 바로 알 수 있습니다.

#5. "Test에서 되던 것이 Local/Prod에 없으면?"

예: users.role 컬럼을 추가한 AddRoleToUsers1765000000000

개발자 PC                CI(빈 MariaDB)              Test DB           Local DB           Prod DB
─────────                ──────────────              ───────           ──────             ───────
entity 수정
migration 생성·리뷰  ─▶  전체 체인 실행               db:setup:test     db:check           백업
커밋 / PR                pending 없음 확인            test:e2e          db:setup           migration:show:prod
                         최신 revert → 재적용                           start:dev          migration:run:prod
                         drift 검사, e2e                                                   pm2:reload → 스모크
  1. 코드를 바꾸면 migration도 같이 만듭니다. entity를 바꾸고 npm run migration:generate -- src/database/migrations/<Name>으로 초안을 만든 뒤, 생성된 SQL을 직접 읽고 다듬습니다. 자동 생성 결과를 그대로 믿지 않습니다.
  2. CI가 빈 DB에서 처음부터 끝까지 적용해 봅니다. "기존 DB에서는 우연히 되는" 변경을 걸러냅니다.
  3. Test DB에서 e2e로 실제 서버 버전과 설정에서 동작을 확인합니다.
  4. Local DB(app_db_dev)는 개발하면서 데이터가 쌓인 DB입니다. 여기서 기존 데이터 위에 적용되는지 확인합니다(예: NOT NULL 컬럼 추가에 default가 필요한지).
  5. Prod는 배포 단계에서 명령으로 적용합니다. 순서는 백업 → 적용 대기 목록 확인 → 적용 → 앱 재시작 → 스모크입니다.

어느 환경에 migration이 없는지는 그 환경에서 db:check(또는 migration:show)를 실행하면 [ ]로 표시됩니다. "직접 만들어야 하나?"에 대한 답은 아니요, 그 환경에서 같은 migration 명령을 실행합니다입니다.

데이터베이스 자체가 없을 때는 환경마다 다르게 처리합니다.

  • Local/Test: db:setup이 만듭니다(앱 전용 이름에 한해, 권한이 DB 단위로 있을 때).
  • Prod: 관리자 SQL로 만듭니다.

#6. 하위 호환 변경: expand → contract

배포 중에는 잠깐이라도 새 스키마와 이전 코드가 함께 돌아갑니다. migration을 먼저 적용하고 앱을 나중에 재시작하기 때문입니다. 그래서 한 번의 배포에서는 이전 코드가 깨지지 않는 변경만 합니다.

하고 싶은 변경 안전한 순서
컬럼 추가 NULL 허용이나 default를 두고 추가합니다(이번 role은 default 'user')
컬럼 삭제 1) 코드에서 사용을 제거하고 배포 → 2) 다음 릴리스에서 migration으로 삭제
컬럼 이름 변경 1) 새 컬럼 추가와 데이터 복사 → 2) 코드 전환 → 3) 이전 컬럼 삭제
NOT NULL로 강화 1) 기존 NULL 데이터 보정 → 2) 제약 추가
큰 테이블 인덱스 트래픽이 적은 시간에 별도 배포로, 소요 시간을 미리 측정

#7. 검증 계층: 어디서 무엇을 증명하나

단계 명령 증명하는 것
단위 테스트 npx jest 로직(예: database-admin.spec.ts의 생성·거부 규칙)
CI database job db:reset:test → db:check:test -- --strict → migration:revert:test + migration:run:test → migration:check:test → test:e2e 빈 DB에서 전체 체인이 적용되는지, 최신 migration의 down/up, entity와 migration 일치(drift), 앱 기동
Test DB db:setup:test, test:e2e 실제 개발 서버 버전과 설정에서 동작
Local DB db:check → db:setup 기존 데이터 위에서 적용
Prod 배포 env:check:prod → db:check:prod → 백업 → migration:show:prod → migration:run:prod → /health 운영 적용과 서비스 정상
앱 기동 MigrationStatusService 로그 적용 누락 감지(경고만)

db:check는 읽기 전용입니다. 계정 권한, 앱 소유 여부, TLS 사용 여부도 보여 주므로 접속·권한·공유 DB 문제를 가장 먼저 확인하는 도구로 씁니다.

2026-11-09에는 실제 개발 서버에서 이 계층을 한 번 끝까지 실행했습니다. app_db_test에 9개 migration 적용, --strict 통과, e2e 통과, db:reset:test 후 재적용까지 확인했고, 같은 서버의 다른 DB는 변경이 없었습니다.

#8. 실패와 롤백

  • migration 실패: 배포를 멈춥니다. 앱은 아직 재시작하지 않았으므로 이전 버전이 계속 동작합니다. 원인을 고친 뒤 다시 실행합니다.
  • revert: migration:revert는 마지막 migration 하나의 down을 실행합니다. 모든 migration이 되돌릴 수 있는 것은 아닙니다.
    • ArchiveLegacyMusicSchema: down이 의도적으로 실패합니다(이름 변경 복구는 백업으로).
    • RepairLegacyMariaDbSchema: down이 아무것도 하지 않습니다(데이터 손실 방지).
  • 그래서 운영 migration 전에는 반드시 백업합니다(mysqldump --single-transaction). 최종 복구 수단은 revert가 아니라 백업입니다.
  • 빈 DB에서 전체 체인을 실행하면 초기 migration이 만든 음악 테이블이 ArchiveLegacyMusicSchema에서 legacy_*로 이름이 바뀝니다. 그래서 새 DB에도 빈 legacy_* 테이블이 생깁니다. 이는 정상입니다.

#8.1 사례: CI가 처음 잡아낸 문제 (2026-11-08)

빈 MariaDB에서 전체 체인을 처음 실행하자, 그동안 기존 DB에서는 드러나지 않던 문제 두 가지가 나왔습니다. "빈 DB에서 처음부터 실행해 보기"가 왜 필요한지 보여 주는 사례입니다.

1) 드라이버가 지원하지 않는 API

  • 오류: AddUniqueEmailToUsers1761000000000 → MySql does not support unique constraints. Use unique index instead.
  • 원인: MariaDB/MySQL에서 UNIQUE는 unique index로 구현됩니다. TypeORM MySQL 드라이버는 createUniqueConstraint·dropUniqueConstraint를 지원하지 않습니다. 이 migration들은 PostgreSQL 시절에 작성됐습니다.
    • 기존 개발 DB에서는 적용 이력만 기록되어 있어서 이 코드가 실행된 적이 없었습니다.
    • 새 개발 서버처럼 빈 DB에 db:setup을 하면 바로 실패했을 문제입니다.
  • 조치: TableIndex({ isUnique: true })로 같은 이름의 unique index를 만들도록 1761과 1762를 고쳤습니다.
  • 이미 적용된 migration을 고쳐도 되는가?
    • 원칙은 "고치지 않는다"입니다.
    • 예외로, 대상 DB에서 아예 실행될 수 없는 migration은 결과 스키마가 같게 고칩니다. 이미 기록된 DB는 다시 실행하지 않으므로 영향이 없습니다.

2) drift: entity와 migration 결과의 차이

migration:check:test가 다음 차이를 보고했습니다(감사 리포트 DB-12).

종류 migration 결과 entity가 기대하는 것
FK·인덱스 이름 FK_track_artist, UQ_users_email 등 명시적 이름 이름을 선언하지 않아 TypeORM 해시 이름(FK_2014e…, IDX_97672…)
시간 컬럼 정밀도 datetime(초 단위) @CreateDateColumn 기본값 datetime(6)
entity에 없는 인덱스 IDX_playlist_track_trackId 등 선언 없음 → 삭제 대상으로 보임
문자셋·타입 표기 legacy_artist.name collation, tinyint(1) 선언 없음

데이터나 기능 문제는 아니지만, 이 상태에서 migration:generate를 실행하면 의도하지 않은 변경(FK 재생성, 인덱스 삭제)이 섞인 초안이 만들어집니다. 해결 방향은 둘 중 하나입니다.

  • 코드를 DB에 맞춤(권장): entity에 이름과 정밀도를 선언합니다. 예: @Index('IDX_…'), @JoinColumn({ foreignKeyConstraintName }), precision: 0. DB 변경이 없습니다.
  • DB를 코드에 맞춤: 보정 migration을 만듭니다. 운영 DDL이 필요합니다.

결정하기 전까지 CI의 drift 단계는 보고만 합니다(continue-on-error).

#8.2 사례: 실제 개발 서버에 처음 연결할 때 (2026-11-09)

1) 비밀번호를 넣었는데 DB_PASSWORD is required.

  • 원인: 비밀번호는 .env.test.local에 넣었는데, 실행한 명령은 Local용 npm run db:check였습니다. 이 명령은 .env를 읽습니다.
  • 교훈: 환경마다 파일이 나뉘어 있으면 "명령 ↔ 파일" 대응을 놓치기 쉽습니다. 그런데 메시지에 어느 파일을 읽었는지가 없어 원인을 바로 알 수 없었습니다.
  • 보완(src/config/env-diagnostics.ts): 검증 실패 메시지에 읽은 파일과 NODE_ENV를 붙입니다. 같은 키가 다른 환경 파일에 있으면 Hint:로 알려 줍니다.
    • 앱 기동, env:check, db:*에 모두 적용했습니다.
    • 다른 파일의 값은 존재 여부만 확인하고 출력하지 않습니다.

2) 접속은 되는데 권한이 부족함

  • 개발 계정은 기존 DB 하나에만 SELECT, INSERT, UPDATE, DELETE, CREATE, INDEX, ALTER 권한이 있었습니다. DROP은 없었습니다.
  • 이 상태로 migration:run을 하면, 1~5번 migration은 적용되고 6번 ArchiveLegacyMusicSchema의 RENAME TABLE에서 실패합니다. RENAME TABLE은 원본 테이블의 DROP 권한이 필요합니다. 결과적으로 DB가 반쯤 바뀐 상태로 남습니다.
  • MariaDB DDL은 트랜잭션으로 되돌릴 수 없으므로(암묵적 커밋), "실패하면 롤백되겠지"가 통하지 않습니다.
  • 보완: db:check와 db:setup이 SHOW GRANTS를 해석해 migration에 필요한 권한(MIGRATION_PRIVILEGES)을 미리 판정합니다.
    • 부족하면 아무것도 바꾸지 않고 멈추고, 빠진 권한만 담은 GRANT SQL을 출력합니다.
    • role 부여처럼 판정할 수 없는 경우에는 막지 않고 경고만 합니다. 오탐으로 작업을 막지 않기 위해서입니다.
  • 실무 원칙: 쓰기 작업 전에 사전 조건(권한, 디스크, 잠금, 백업)을 읽기 전용으로 확인하고, 실패할 것이 확실하면 시작하지 않습니다(fail fast). 중간 실패를 복구하는 것보다 시작 전에 막는 편이 훨씬 쌉니다.

#8.3 사례: 같은 서버의 다른 DB를 지키기 (2026-11-09)

상황

  • 개발 서버에는 이 앱과 상관없는 DB가 함께 있습니다.
  • 처음에는 계정이 이미 권한을 가진 기존 DB를 Local DB로 쓰려 했습니다. 그런데 그 DB에 DROP 권한을 주는 것은 "기존 DB는 삭제하면 안 된다"는 원칙과 충돌했습니다.

점검: 이 앱이 무언가를 지울 수 있는 경로

경로 위험 조치
DB_SYNCHRONIZE=true entity와 다른 컬럼·인덱스를 TypeORM이 자동 삭제할 수 있음. 전에는 Prod에서만 막았음 모든 환경에서 거부
db:setup 대상 DB에 다른 앱 테이블이 있어도 migration 진행. 이름이 겹치면 충돌 앱이 관리하지 않는 객체가 있으면 아무것도 하지 않고 거부
db:reset:test 이름이 *_test이면 안의 객체까지 DROP DATABASE 앱 소유(APP_TABLES만 있음)일 때만 초기화
migration RENAME/ALTER/DROP TABLE(down) 대상 DB 안의 앱 테이블에만 실행(소스 확인, spec으로 고정)
GRANT DROP 권한이 기존 DB 전체에 미침 앱 전용 DB(app_db_dev, app_db_test) 단위로만 권한 부여

결정: 기존 DB는 그대로 두고, 앱 전용 DB app_db_dev를 새로 쓰기로 했습니다.

구현 포인트

  • 소유 판정(inspectOwnership): information_schema의 TABLES(뷰·시퀀스 포함), ROUTINES, EVENTS를 읽어 APP_TABLES에 없는 객체를 찾습니다.
  • 목록 누락 방지: spec이 entity 메타데이터와 migration 소스(new Table({ name }), RENAME … TO …)를 APP_TABLES와 대조합니다. 새 테이블을 만들고 목록에 추가하지 않으면 테스트가 실패합니다.
  • 쓰기 범위 고정: 쓰기 SQL이 대상 DB 이름 외의 식별자를 참조하지 않는지 spec이 검사합니다.

실무 원칙

  • 파괴적 명령은 "무엇을 지워도 되는가"를 이름이 아니라 내용으로 확인합니다. *_test라는 이름만으로는 안전을 보장할 수 없습니다.
  • 공유 서버에서는 앱마다 DB와 권한을 분리합니다. 한 계정의 권한이 다른 앱의 DB에 미치지 않게 합니다.

#8.4 사례: 보안 수정에 필요한 컬럼 추가 (2026-11-09)

비밀번호를 바꿔도 기존 토큰이 살아 있는 문제(AUTH-3)를 고치려고 users.sessionVersion을 추가했습니다(보안 감사). 작은 변경이지만 이 가이드의 원칙을 처음부터 끝까지 따른 예입니다.

단계 한 일 원칙
설계 INT UNSIGNED NOT NULL DEFAULT 0. 기존 행은 자동으로 0이 되고, 0은 "옛 토큰(sv 없음)"과 같은 뜻 추가 전용(expand). 기존 데이터와 기존 토큰을 바꾸지 않음
작성 migration과 entity에 같은 타입·기본값을 씀 drift를 늘리지 않음
읽기 전용 확인 db:check:test → ownership dedicated, 1 pending 쓰기 전에 대상과 상태를 확인
적용 db:setup:test → db:check:test --strict(0 pending) 명령으로 적용
되돌리기 검증 migration:revert:test → migration:run:test down이 실제로 동작하는지 확인
drift 확인 migration:check:test에 sessionVersion이 없음 새 차이가 없음을 확인
동작 확인 e2e, HTTP 스모크(비밀번호 변경 후 이전 토큰 401) 기능까지 확인

배포 순서의 함정: 컬럼을 되돌릴 때는 앱을 먼저 이전 빌드로 돌려야 합니다. 새 코드는 entity가 이 컬럼을 조회하므로, 컬럼부터 지우면 모든 사용자 조회가 실패합니다. 추가는 "DB 먼저, 앱 나중", 제거는 "앱 먼저, DB 나중"입니다.

앞으로의 DB 과제(drift 해소, 계정 분리, 백업 자동화 등)는 DB 개선 가이드에 우선순위와 단계로 정리했습니다.

#9. 이 프로젝트의 구현

역할 코드
환경별 env 파일 선택 src/config/env-files.ts
설정 오류에 읽은 파일·Hint 추가 src/config/env-diagnostics.ts
환경변수 검증(test는 *_test만, synchronize 금지) src/config/app-env.ts
TypeORM 옵션, migration 경로, TLS src/database/database-options.ts
migration CLI용 data-source src/database/data-source.ts
DB 확인·생성·초기화, 권한 판정(evaluatePrivileges), 소유 판정(inspectOwnership, APP_TABLES) src/database/database-admin.ts
db:check / db:ensure / db:reset CLI src/database/cli/db-tool.ts
환경별 실행 래퍼(--dist 포함) scripts/typeorm-env.cjs
기동 시 pending 경고 src/database/migration-status.service.ts
CI 검증 job .github/workflows/ci.yml database
migration 파일 src/database/migrations/

설계 포인트:

  • DB를 지정하지 않고 접속합니다. db-tool은 서버에만 연결합니다. 대상 DB가 아직 없어도 확인하고 만들 수 있게 하기 위해서입니다.
  • 허용되지 않는 명령은 연결 전에 거부합니다. prod의 ensure, test가 아닌 환경의 reset이 해당합니다.
  • DB 이름은 영문, 숫자, _, -만 허용합니다. 식별자는 SQL 파라미터로 바인딩할 수 없어 백틱으로 직접 넣기 때문입니다. 백틱과 따옴표는 허용하지 않습니다.
  • 쓰기 전에 읽기 전용으로 확인합니다. 권한, 소유, 존재 여부를 모두 확인한 다음에만 CREATE/DROP을 실행합니다.
  • 대상 DB 하나만 다룹니다. 다른 DB는 목록 조회(SHOW DATABASES) 외에는 접근하지 않습니다.
  • 비밀번호는 어디에도 출력하지 않습니다. SHOW GRANTS의 해시도 가립니다.
  • 같은 규칙을 한 곳에서 씁니다. 앱, migration CLI, db-tool, e2e가 같은 env 파일 규칙과 같은 검증(validateAppEnv)을 씁니다.

#10. 결정 기록 (2026-11-08 ~ 11-09)

결정 이유
Local과 Test를 같은 외부 개발 서버에 두고, 같은 개발 계정을 사용 서버가 하나입니다. 데이터베이스 이름 규칙(*_test)으로 e2e가 개발 데이터를 바꾸지 못하게 합니다
데이터베이스와 테이블은 명령으로 생성(db:setup), 기동 시 자동 실행은 하지 않음 4장의 실패, 재시작 반복, 공유 DB 문제
비밀번호는 각 env 파일(.env, .env.test.local)에 직접 입력 Git 미추적 파일, 권한 600. 채팅·문서·커밋에 남기지 않음
개발 서버는 TLS 미지원. DB_SSL=false를 유지하고 접근을 IP로 제한하거나 SSH 터널 사용 인터넷 구간에서 계정 정보가 평문으로 오가므로 노출 범위를 줄입니다
CI에 MariaDB 10.11 job 추가 실제 MariaDB에서 migration 전체 체인을 검증한 적이 없었습니다(감사 미검증 항목)
(2026-11-09 오전) Local은 서버에 이미 있던 빈 DB를 사용하기로 함. 이름의 -를 허용 관리자 작업이 DROP 하나로 줄어든다고 판단했습니다. 같은 날 아래 결정으로 대체
(2026-11-09) 권한 사전 점검을 db:setup의 필수 단계로 둠 권한 부족으로 migration이 중간에서 멈추면 DDL을 되돌릴 수 없습니다(8.2)
(2026-11-09) 환경 용어를 Local / Test / Prod로 통일. 파일과 명령은 유지 실제 운용(PC에서 개발, EC2에서 운영)과 이름을 맞춥니다
(2026-11-09) Local은 앱 전용 새 DB app_db_dev를 사용. 기존 DB는 사용하지 않음 기존 DB에 DROP 권한을 주지 않기 위해서입니다(8.3)
(2026-11-09) db:setup·db:reset은 앱 소유 DB에서만 동작. synchronize는 모든 환경에서 금지 다른 앱의 객체와 데이터를 어떤 경우에도 지우지 않기 위해서입니다(8.3)
(2026-11-09) 토큰 무효화는 users.sessionVersion 컬럼으로 추가 전용 변경이라 기존 데이터·토큰에 영향이 없습니다(8.4)

#11. 자가 점검 질문

  1. 운영에서 db:ensure를 막은 이유는 무엇인가? 앱 계정에 어떤 권한이 있으면 위험한가?
  2. synchronize: true를 운영에서 쓰면 어떤 일이 생길 수 있는가? 컬럼 이름 변경을 예로 설명해 보라.
  3. CI에서 빈 DB 전체 실행과 drift 검사는 각각 어떤 실수를 잡는가?
  4. 컬럼을 삭제하는 변경을 한 번의 배포로 하면 배포 도중 어떤 오류가 날 수 있는가?
  5. migration:revert로 되돌릴 수 없는 migration이 있을 때 운영 복구 수단은 무엇인가?
  6. 앱 기동 시 pending migration을 발견했을 때 자동 적용 대신 경고만 하는 이유는?
  7. RENAME TABLE에는 왜 DROP 권한이 필요한가? 권한 없이 migration을 시작하면 DB는 어떤 상태로 남는가?
  8. npm run db:check와 npm run db:check:test는 각각 어느 파일을 읽는가? 셸에 export한 DB_PASSWORD가 있으면 어느 값이 쓰이는가?
  9. db:reset:test가 이름(*_test)만 보고 DB를 지우면 어떤 사고가 날 수 있는가? 이 프로젝트는 무엇을 추가로 확인하는가?
  10. 새 테이블을 만드는 migration을 추가할 때 APP_TABLES도 고쳐야 하는 이유는? 고치지 않으면 무엇이 알려 주는가?
  11. 컬럼을 추가할 때와 제거할 때 앱과 DB의 배포 순서가 반대인 이유는 무엇인가?(8.4)

#12. 실습 과제

  1. npm run db:check의 출력에서 서버 버전, TLS, 권한(privilege), 소유(ownership), pending 목록을 읽어 보세요.
  2. npm run db:reset:test 후 npm run db:check:test로 빈 DB에서 전체 체인이 적용되는 것을 확인하세요.
  3. users에 NULL 허용 컬럼을 추가하는 entity 변경을 하고, migration:generate로 초안을 만들어 SQL을 리뷰하세요. 실습 후에는 되돌립니다.
  4. 3번을 커밋하지 않은 상태에서 npm run migration:check:test를 실행해 drift가 어떻게 보고되는지 확인하세요.
  5. migration:revert:test로 마지막 migration을 되돌리고, 앱 기동 로그에 pending 경고가 나오는지 확인한 뒤 다시 적용하세요.
  6. database-admin.spec.ts의 inspectOwnership·resetTestDatabase 테스트를 읽고, 다른 앱의 테이블이 섞인 DB를 db:reset이 어떻게 거부하는지 설명해 보세요.
