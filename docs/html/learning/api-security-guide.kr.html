API 보안 학습 가이드: 이 프로젝트로 배우는 인증·인가·입력·운영 보안

최신화 기준: 2026-11-09 · develop 9b731ef + chore/project-audit-2026-11 근거와 ID: 2026-11-09 보안 감사 · 비밀 관리와 push 전 점검: 시크릿 관리 가이드 · 용어: 용어집

#1. 학습 목표

이 문서를 읽고 나면 다음을 설명할 수 있어야 합니다.

  • 이 API의 자산, 공격자, 진입점(위협 모델)
  • 비밀번호를 어떻게 저장하고 비교하는지, bcrypt의 72바이트 한계가 무엇인지
  • IP 단위 제한과 계정 단위 제한이 각각 무엇을 막는지
  • JWT 세션을 어떻게 "취소"할 수 있는지(sessionVersion)
  • 외부 IdP 토큰을 받을 때 무엇을 반드시 검증해야 하는지(aud, iss, 발급 앱)
  • 경로 문자열로 보안 판단을 하면 왜 위험한지(SEC-17 사례)
  • 설정이 비었을 때 "통과"가 아니라 "거부"해야 하는 이유(fail-closed)
  • 직접 보안 점검을 하는 순서와 명령

#2. 위협 모델

구분 이 프로젝트에서
지켜야 할 것(자산) 사용자 계정(비밀번호 해시, email), 세션 JWT, admin 권한, 음악 카탈로그 데이터, JWT_SECRET·DB 계정 같은 비밀값, 같은 DB 서버의 다른 DB
공격자 인터넷의 익명 사용자, 가입한 일반 사용자, 토큰을 훔친 사람, 다른 SNS 앱 운영자(그 앱 사용자의 토큰을 가진 사람), 의존성 공급망
진입점 공개 라우트(가입, 로그인, SNS 로그인, 음악 조회), JWT 라우트, admin 라우트, 배포 스크립트와 CI, 개발자 PC의 env 파일
신뢰 경계 클라이언트 → (nginx) → Nest 앱 → MariaDB / 외부 IdP(Google, Apple, Kakao, Naver, Facebook)

요청이 지나는 순서와 각 단계의 방어 장치는 다음과 같습니다.

요청
 └─ helmet, CORS(origin 목록), body 크기(기본 100kb)
 └─ RequestIdInterceptor ........ x-request-id 형식 검사(SEC-14)
 └─ ThrottlerGuard .............. IP 단위 제한(전역 10회/60초, 로그인 5회/분)
 └─ ProviderReadinessGuard ...... 비활성 SNS provider 503(라우트 메타데이터 기준, SEC-17)
 └─ JwtAuthGuard / RolesGuard ... 토큰 서명·만료·sessionVersion, admin 역할
 └─ ValidationPipe .............. whitelist, forbidNonWhitelisted, 길이 상한(SEC-18)
 └─ use-case .................... 계정 단위 실패 제한(SEC-19), 비즈니스 규칙
 └─ GlobalExceptionFilter ....... 5xx 메시지 고정, 비밀값 마스킹, 로그 redaction

#3. 비밀번호 저장과 비교

bcrypt를 쓰는 이유: 해시 계산이 의도적으로 느리고(cost 10 = 2^10회 반복) salt가 자동으로 들어갑니다. DB가 유출돼도 비밀번호를 한꺼번에 알아내기 어렵습니다.

bcrypt의 72바이트 한계

  • bcrypt는 입력의 앞 72바이트만 사용합니다.
  • 예를 들어 73바이트 비밀번호 A…A1과 A…A2는 같은 해시로 검증됩니다.
  • UTF-8에서 한글 한 글자는 3바이트이므로, 한글 25자(75바이트)도 이미 한계를 넘습니다.
  • 그래서 새 비밀번호는 72바이트 이하만 받습니다(@IsByteLength(0, 72)).
  • 로그인과 현재 비밀번호 확인에는 72바이트 제한을 걸지 않습니다. 정책 이전에 긴 비밀번호로 가입한 사용자도 로그인할 수 있어야 하기 때문입니다. 요청 크기만 1024자로 제한합니다.

최소 길이를 8자로 한 이유: NIST SP 800-63B는 사용자가 고르는 비밀번호에 최소 8자를 권장합니다. 복잡도 규칙(대문자, 특수문자 강제)보다 길이와 유출 목록 대조가 효과적이라고 봅니다. 유출 비밀번호 대조는 이 프로젝트에 아직 없습니다.

응답 시간으로 계정 존재가 드러나지 않게 하기(SEC-9)

  • 계정이 없을 때 bcrypt를 건너뛰면 응답이 눈에 띄게 빨라집니다.
  • 그래서 계정이 없어도 고정 해시와 한 번 비교합니다(bcrypt-password-hasher.adapter.ts).

정책 값은 한곳에 모아 두었습니다: src/users/domain/user-input-policy.ts

#4. 무차별 대입: IP 단위와 계정 단위

제한 막는 것 못 막는 것 위치
IP 단위(5회/분) 한 IP에서 빠르게 반복 시도 여러 IP(봇넷, 프록시)로 나눠 한 계정을 공격 @Throttle
계정 단위(실패 10회/15분) IP를 바꿔 가며 한 계정을 공격 계정마다 비밀번호 한두 개씩 시도하는 credential stuffing InMemoryLoginAttemptLimiterAdapter

설계에서 고민한 점

  • 실패만 셉니다. 성공하면 초기화하므로 정상 사용자는 거의 걸리지 않습니다.
  • 없는 계정도 똑같이 셉니다. 그렇지 않으면 "차단되는 계정은 존재한다"는 정보가 새어 나갑니다.
  • 식별자를 정규화합니다. Alice, alice가 다른 키가 되면 우회됩니다.
  • 잠금(lockout) DoS: 공격자가 피해자 계정을 일부러 실패시켜 잠글 수 있습니다. 영구 잠금이 아니라 15분 창으로 제한해 피해를 줄였습니다. 실무에서는 CAPTCHA, 점진적 지연, 신뢰 기기 예외를 함께 씁니다.
  • 저장소: 프로세스 메모리라 PM2 인스턴스가 하나일 때만 정확합니다. 인스턴스를 늘리면 Redis 같은 공유 저장소 어댑터로 바꿉니다. 포트(LoginAttemptLimiterPort)를 두었기 때문에 use-case는 바뀌지 않습니다.

#5. 세션 JWT와 "취소"

JWT의 장단점: 서버가 세션을 저장하지 않아 단순하지만, 한 번 발급한 토큰을 만료 전에 무효로 만들기 어렵습니다.

이 프로젝트의 선택: 세션 버전(sessionVersion)

  1. users.sessionVersion(기본 0)을 둡니다(migration 1766).
  2. 토큰을 발급할 때 현재 버전을 sv claim에 넣습니다.
  3. JwtStrategy는 이미 매 요청 사용자를 DB에서 다시 읽고 있습니다(역할 변경을 즉시 반영하려고). 여기서 sv와 DB 값을 함께 비교합니다. 추가 쿼리가 없습니다.
  4. 비밀번호를 바꾸면 버전을 1 올립니다. 그 전에 발급된 토큰은 모두 401이 됩니다.
방식 장점 단점
짧은 만료만 사용 구현 없음 만료 전까지는 못 막음
세션 버전(이번 선택) 컬럼 하나, 추가 쿼리 없음 사용자 단위로만 취소(기기별 로그아웃 불가)
토큰 블랙리스트(jti 저장) 토큰 단위 취소 저장소가 필요하고 매 요청 조회
refresh token + 짧은 access token 실무 표준, 기기별 관리 테이블과 rotation 로직 필요(📌 P1)

하위 호환: 배포 전에 발급된 토큰에는 sv가 없습니다. 없으면 0으로 간주하므로 배포 직후 모든 사용자가 로그아웃되지 않습니다. 대신 비밀번호를 한 번이라도 바꾼 사용자의 옛 토큰은 거부됩니다.

#6. 인가: 누가 무엇을 할 수 있나

  • 인증과 인가는 다릅니다. 로그인했다는 사실(인증)만으로 쓰기 권한(인가)을 주면 안 됩니다(SEC-1).
  • @AdminOnly() = JwtAuthGuard + RolesGuard + @Roles(admin)
  • 역할은 토큰이 아니라 매 요청 DB에서 읽습니다. 권한을 회수하면 즉시 반영됩니다.
  • 빠뜨림을 테스트로 막기: music-authorization.spec.ts는 컨트롤러 메타데이터를 읽어, 쓰기 라우트에 admin 역할이 없으면 실패합니다. 같은 방식으로 SNS 컨트롤러의 @SocialProviderRoute도 검사합니다.

#7. 외부 IdP 토큰 검증

다른 회사가 발급한 토큰을 받을 때는 "누가, 누구에게, 언제" 발급했는지 모두 확인해야 합니다.

검증 의미 빠지면
서명 provider가 발급했는가 위조 토큰 통과
iss (issuer) 기대한 provider인가 다른 발급자의 토큰 통과
aud (audience) / 발급 앱 이 앱을 위해 발급했는가 토큰 치환: 다른 앱이 받은 사용자 토큰으로 이 서비스에 로그인
exp 만료되지 않았는가 오래된 토큰 재사용
nonce 이 로그인 시도에서 받은 토큰인가 재전송(replay)

provider별 방법:

  • Google, Apple: ID Token(JWT)의 aud를 허용 목록(GOOGLE_ALLOWED_AUDIENCES, APPLE_ALLOWED_AUDIENCES)과 비교합니다.
  • Kakao: access token은 JWT가 아니므로 /v1/user/access_token_info의 app_id를 KAKAO_APP_ID와 비교합니다.
  • Facebook: debug_token으로 app_id를 확인합니다.
  • Naver: 발급 앱을 확인할 공식 방법을 찾지 못했습니다. 그래서 클라이언트 access token 로그인을 기본으로 막고, 서버가 code를 직접 교환하는 흐름만 허용합니다.

토큰 치환 공격의 흐름

  1. 공격자가 "운세 보기" 같은 앱을 만들어 Kakao 로그인을 붙입니다.
  2. 피해자가 그 앱에 로그인하면 공격자는 피해자의 Kakao access token을 얻습니다.
  3. 공격자는 그 토큰을 이 서비스의 POST /auth/kakao/login에 보냅니다.
  4. 서버가 프로필 조회만 하고 발급 앱을 확인하지 않으면, 공격자는 피해자로 로그인합니다.

#8. 사례: 대소문자 경로로 비활성 provider 우회 (SEC-17)

상황: SNS 로그인은 모두 꺼져 있었습니다. 꺼진 provider는 ProviderReadinessGuard가 503으로 막는다고 생각했습니다.

결함

// 수정 전: 요청 경로를 정규식으로 검사
const match = /^\/auth\/([^/]+)/.exec(request.path);   // 'GOOGLE'은 목록에 없음 → 통과
  • Express는 기본적으로 대소문자를 구분하지 않고 라우팅합니다. 그래서 /auth/GOOGLE/login도 Google 컨트롤러로 갑니다.
  • 가드는 GOOGLE을 알 수 없는 provider로 보고 통과시켰습니다.

피해가 커진 이유: fail-open 설정

  • 꺼진 provider에는 설정이 없습니다. 그런데 검증 코드는 설정이 없으면 검사를 생략했습니다.
    • Google: audience: allowed.length > 0 ? allowed : undefined → aud 검사 없음
    • Kakao: KAKAO_APP_ID가 없으면 경고만 하고 통과
  • 두 결함이 겹쳐서 "꺼져 있다"고 믿은 기능이 가장 약한 설정으로 동작했습니다.

재현: 수정 전 커밋(532ccc7)을 빌드해서 확인했습니다.

요청 결과
POST /auth/google/verify-id-token 503 AUTH_GOOGLE_DISABLED
POST /auth/GOOGLE/verify-id-token 500 AUTH_GOOGLE_INTERNAL_ERROR — 컨트롤러와 검증기까지 실행됨

수정

  1. 경로가 아니라 라우트 메타데이터로 판정합니다. 컨트롤러에 @SocialProviderRoute('google')을 붙이고, 가드는 Reflector로 읽습니다. 라우터가 어떤 철자로 매칭했든 실행될 컨트롤러는 같으므로 우회할 수 없습니다.
  2. 설정이 없으면 거부합니다(fail-closed). audience나 KAKAO_APP_ID가 비면 *_CONFIG_MISSING(503)을 반환합니다.
  3. 테스트로 고정합니다. 메타데이터가 빠진 SNS 컨트롤러가 있으면 spec이 실패합니다. e2e는 대소문자를 바꾼 경로가 503인지 확인합니다.

일반화한 교훈

  • 보안 판단은 라우터가 내린 결정(어느 핸들러가 실행되는가)에 붙입니다. 경로 문자열을 다시 해석하지 않습니다. 대소문자, 끝의 /, URL 인코딩, 전역 prefix, 버전 경로처럼 라우터와 다르게 해석할 여지가 많습니다.
  • "기능이 꺼져 있다"는 것은 방어가 아닙니다. 꺼진 기능의 코드도 안전한 기본값을 가져야 합니다.
  • 방어는 겹쳐 둡니다(심층 방어). 가드가 뚫려도 검증기가 거부하면 피해가 없습니다.

#9. 입력 검증

  • whitelist + forbidNonWhitelisted: DTO에 없는 필드는 400입니다. role: 'admin'을 끼워 넣어도 거부됩니다(대량 할당 방지).
  • 모든 문자열에 상한을 둡니다. 상한이 없으면 다음 일이 생깁니다.
    • DB 컬럼보다 길면 Data too long 오류로 500
    • 거대한 문자열이 외부 API 호출, 로그, 정규식으로 흘러감
  • LIKE 패턴 이스케이프: %, _는 LIKE의 와일드카드입니다. 사용자 입력을 그대로 넣으면 % 하나로 전체를 조회하거나 패턴으로 비용을 키울 수 있습니다. escapeLike()로 \ % _를 이스케이프합니다. SQL 주입은 바인딩 파라미터로 막고, 패턴 조작은 이스케이프로 막습니다. 둘은 다른 문제입니다.
  • URL 필드: scheme을 http, https로 제한합니다. javascript: 같은 값이 저장되면 그 값을 링크로 쓰는 클라이언트에서 문제가 됩니다.

#10. 오류와 로그

  • 5xx 메시지는 고정합니다(Internal server error). 원인은 requestId와 함께 서버 로그에만 남깁니다(SEC-4).
  • 로그에 비밀값을 남기지 않습니다. redactSensitiveText가 password=, token=, Bearer …, DB URL 비밀번호를 가립니다. 이번에 로그의 path(query 포함)에도 적용했습니다(SEC-23).
  • 클라이언트가 보낸 값은 로그에 그대로 쓰지 않습니다. x-request-id는 안전한 문자와 길이일 때만 쓰고, 아니면 새로 만듭니다(SEC-14).
  • 남은 과제: provider 오류 원문이 401 메시지로 나갑니다(SEC-24).

#12. 직접 보안 점검하는 방법

이번 감사에서 쓴 순서입니다. 새 기능을 넣은 뒤 같은 순서로 다시 확인할 수 있습니다.

  1. 라우트와 권한 목록 뽑기: 모든 라우트의 메서드, 경로, 가드를 표로 만듭니다(API 명세). 공개 라우트부터 봅니다.
  2. 가드가 무엇을 기준으로 판단하는지 확인: 경로 문자열, 헤더처럼 공격자가 바꿀 수 있는 값을 기준으로 하면 의심합니다.
  3. 설정이 비었을 때 동작 확인: if (config) check() 형태를 찾습니다. 비었을 때 통과하면 fail-open입니다.
    grep -rn "length > 0 ?" src/auth
grep -rn "skipping\|skip" src --include=*.ts
  4. 입력 상한 확인: @IsString()만 있고 @MaxLength가 없는 필드를 찾습니다.
  5. 외부 토큰 검증 확인: aud·iss·발급 앱을 확인하는지 provider별로 봅니다.
  6. 오류와 로그 확인: 5xx 응답에 원문이 나가는지, 로그에 비밀값이 남는지 봅니다.
  7. 공급망과 이력: npm audit --omit=dev, Git 이력 비밀값 검색(시크릿 관리 가이드 3장)
  8. 재현과 회귀 테스트: 결함은 수정 전 코드에서 재현하고, 같은 요청을 e2e나 spec으로 고정합니다.

#13. 결정 기록 (2026-11-09)

결정 이유
가드는 경로 대신 메타데이터로 판정 라우터와 같은 결론을 보장. 라우팅 옵션을 바꾸는 방식(case sensitive routing 켜기)은 기존 클라이언트를 깨뜨릴 수 있음
설정 누락은 503 CONFIG_MISSING 401은 "토큰이 틀림"으로 읽혀 원인을 숨김. 운영자가 설정 문제임을 알 수 있어야 함
세션 무효화는 sessionVersion 이미 매 요청 사용자를 조회하므로 추가 비용 없음. refresh token은 별도 설계(P1)
비밀번호 변경 후 현재 토큰도 무효 탈취된 토큰과 현재 토큰을 구분할 수 없음. 다시 로그인하게 하는 것이 일반적
계정 단위 제한은 메모리 저장 현재 단일 인스턴스. 포트로 분리해 Redis 전환 비용을 낮춤
새 비밀번호만 8자·72바이트 정책 기존 사용자의 로그인을 깨지 않음

#14. 자가 점검 질문

  1. /auth/GOOGLE/login이 Google 컨트롤러로 라우팅되는 이유는 무엇인가요? 가드를 메타데이터 기준으로 바꾸면 왜 해결되나요?
  2. "설정이 없으면 검사를 생략한다"는 코드가 위험한 이유를 SEC-17로 설명해 보세요.
  3. bcrypt에 73바이트 비밀번호를 넣으면 어떤 일이 생기나요? 그런데 왜 로그인 DTO에는 72바이트 제한을 걸지 않았나요?
  4. IP 단위 제한과 계정 단위 제한은 각각 어떤 공격을 막고, 어떤 공격은 못 막나요?
  5. 계정 단위 제한에서 없는 계정도 실패로 세는 이유는 무엇인가요?
  6. sessionVersion을 도입해도 배포 직후 모든 사용자가 로그아웃되지 않는 이유는 무엇인가요?
  7. Kakao access token으로 로그인할 때 프로필 조회만 하면 어떤 공격이 가능한가요?
  8. SQL 주입 방어(바인딩 파라미터)가 있는데도 escapeLike가 필요한 이유는 무엇인가요?
  9. 클라이언트가 보낸 x-request-id를 그대로 로그에 쓰면 어떤 문제가 생기나요?
