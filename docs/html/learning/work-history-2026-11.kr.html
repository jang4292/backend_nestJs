원인

#3단계: 환경별 env 파일과 SNS 로그인 비활성화

문제

  • 앱, migration CLI, e2e가 env 파일을 각자 다르게 골랐습니다. 운영 전용 파일이 없었습니다.
  • Google은 플래그가 없으면 기본으로 켜졌습니다. 다른 provider는 키만 있으면 자동으로 켜졌습니다. 그래서 설정이 빠지면 운영 기동이 실패하거나, 의도치 않게 provider가 켜졌습니다.
  • e2e가 개발 DB(app_db)를 쓸 수 있는 예외가 있었습니다.

조치

  • src/config/env-files.ts 하나로 파일을 고르게 했습니다: .env / .env.test.local / .env.production, ENV_FILE로 재지정 가능
  • env:check[:test|:prod]: DB에 접속하지 않고 설정만 검증합니다.
  • migration:*:prod: dist 기반으로 실행해 운영 서버에 ts-node가 필요 없게 했습니다.
  • SNS 5종을 명시적 opt-in으로 바꾸고 현재는 모두 껐습니다. Naver accessToken 로그인은 기본 차단합니다(SEC-3).
  • test 환경은 *_test DB만 허용합니다.

배운 점

  • "설정이 없으면 켜진다"는 기본값은 위험합니다. 위험한 기능은 명시적으로 켜게 합니다.
  • 같은 규칙(파일 선택, 검증)을 모든 진입점이 공유해야 "로컬에서는 되는데 migration은 안 되는" 일이 사라집니다.

자료: 환경별 DB·설정 가이드, SNS 재활성화 체크리스트, SNS 운영 가이드

#4단계: DB 도구, CI MariaDB 검증, migration 결함

문제

  • DB나 테이블을 언제, 어떻게 만드는지 정해져 있지 않았습니다.
  • migration 전체 체인을 실제 MariaDB에서 실행해 본 적이 없었습니다.

조치

  • db:check(읽기 전용)와 db:setup(DB가 없으면 생성 + migration)을 추가했습니다.
  • 앱 기동 시 pending migration을 경고합니다(MigrationStatusService). 자동 실행은 하지 않습니다.
  • CI database job(MariaDB 10.11): 빈 DB → 전체 체인 → pending 없음 → 최신 revert/재적용 → drift → e2e

CI가 처음 실행되자 드러난 결함

  • DB-13: 1761·1762 migration이 MariaDB 드라이버가 지원하지 않는 createUniqueConstraint를 써서, 빈 DB에서는 체인이 실패했습니다. 기존 DB에는 이력만 기록되어 있어 드러나지 않았습니다. 같은 이름의 unique index로 고쳤습니다.
  • DB-12: entity와 migration 결과가 다릅니다(FK·인덱스 이름, datetime 정밀도). 해결 방향은 결정이 필요하며, 지금은 CI에서 보고만 합니다.

배운 점

  • 빈 DB에서 처음부터 실행해 보는 검증만이 "기존 DB에서는 우연히 되는" 결함을 잡습니다.
  • migration은 명령으로 적용합니다. 기동 시 자동 실행은 실패하면 재시작을 반복하고, 공유 DB를 바꿉니다.

자료: DB·스키마 관리 학습 가이드 4~8.1장

#5단계: 첫 실서버 연결, env 파일 진단과 권한 사전 점검

문제 1: .env.test.local에 비밀번호를 넣고 npm run db:check를 실행했더니 DB_PASSWORD is required.가 나왔습니다.

  • 원인: 이 명령은 .env를 읽습니다. 그런데 오류에 어느 파일을 읽었는지가 없었습니다.
  • 조치(env-diagnostics.ts)
    • 오류에 읽은 파일과 NODE_ENV를 붙입니다.
    • 다른 환경 파일에 그 키가 있으면 Hint:를 출력합니다(값은 출력하지 않음).

문제 2: 계정에 DROP 권한이 없어, migration이 6번째 RENAME TABLE에서 중간 실패할 상태였습니다.

  • MariaDB DDL은 되돌릴 수 없어 DB가 반쯤 바뀐 상태로 남습니다.
  • 조치: SHOW GRANTS를 해석해 필요한 8개 권한을 미리 판정합니다(evaluatePrivileges).
    • 부족하면 db:setup이 아무것도 바꾸지 않고 멈추고, 빠진 권한만 담은 GRANT를 출력합니다.

배운 점

  • 오류 메시지는 "무엇이"뿐 아니라 "어디서"를 말해야 합니다.
  • 되돌릴 수 없는 작업은 사전 조건을 읽기 전용으로 확인한 뒤 시작합니다(fail fast).

자료: DB·스키마 관리 학습 가이드 8.2

#6단계: Local / Test / Prod 정리와 다른 DB 삭제 방지

요청: local, dev, prod를 다시 정리하고, DB 서버에 있는 다른 DB는 절대 삭제하지 않습니다.

점검 결과(삭제 위험 경로)

  • DB_SYNCHRONIZE=true는 Prod에서만 막았습니다. Local/Test에서 켜면 컬럼이 자동 삭제될 수 있었습니다.
  • db:setup은 다른 앱 테이블이 있는 DB에서도 진행했습니다.
  • db:reset:test는 이름(*_test)만 보고 DB 전체를 지웠습니다.

조치

항목 내용
환경 용어 Local(개발 PC + 개발 서버 DB), Test(Local 안의 e2e), Prod(EC2)로 통일. 파일과 명령은 유지
Local DB 앱 전용 새 DB app_db_dev. 기존 DB는 사용하지 않음
소유 판정 APP_TABLES와 inspectOwnership으로 대상 DB에 앱이 아닌 객체가 있는지 확인
거부 동작 다른 객체가 있으면 db:setup·db:reset이 아무것도 바꾸지 않고 거부. db:check는 ownership: shared로 경고
synchronize 모든 환경에서 기동 거부
보증 테스트 쓰기 SQL이 대상 DB 외에는 참조하지 않는지 spec으로 고정. APP_TABLES와 entity·migration을 대조

실서버 확인

  • app_db_test 생성과 9개 migration 적용, --strict 통과, e2e 통과
  • db:reset:test가 소유를 확인한 뒤 초기화하고 다시 적용
  • 같은 서버의 다른 DB는 변경 없음(0 tables 유지)

배운 점

  • 파괴적 명령은 이름이 아니라 내용으로 안전을 확인합니다.
  • 공유 서버에서는 앱마다 DB와 권한을 분리합니다. GRANT는 앱 DB 단위로만 줍니다.

자료: 환경별 가이드 2장 DB 삭제 안전 원칙, DB·스키마 관리 학습 가이드 8.3

#7단계: 보안 전수 감사

요청: 보안 관련 전수 감사를 하고, 개선 방향을 적용하고, 관련 코드와 문서를 보완합니다. DB 관련 개선 방향도 가이드로 정리합니다.

가장 큰 발견: 꺼진 SNS 로그인이 대소문자를 바꾼 경로로 열림(SEC-17, High)

  • 문제: POST /auth/GOOGLE/verify-id-token이 비활성 가드를 통과해 컨트롤러까지 실행됐습니다(수정 전 커밋을 빌드해 500으로 재현).
  • 원인 1: Express는 기본적으로 대소문자를 구분하지 않고 라우팅합니다. 가드는 경로를 대소문자 구분 정규식으로 검사했습니다.
  • 원인 2: 꺼진 provider는 설정이 비어 있는데, 검증 코드는 설정이 비면 검사를 생략했습니다(Google·Apple은 audience 없이, Kakao는 app_id 확인 없이). 두 결함이 겹쳐 다른 앱에서 발급된 토큰으로 계정이 생기고 세션이 발급되는 상태였습니다.
  • 조치
    • 가드가 경로 대신 컨트롤러 메타데이터(@SocialProviderRoute)로 판정합니다.
    • 설정이 비면 거부합니다(fail-closed). KAKAO_APP_ID는 Kakao가 켜지면 모든 환경에서 필수입니다.
    • 메타데이터 누락 spec과 대소문자 경로 e2e로 고정했습니다.

  • app_db_test에 1766 적용 → --strict → revert/재적용 → drift 확인(새 차이 없음) → e2e 5/5
  • 빌드 결과 HTTP 스모크 16/16. 임시 사용자는 만든 뒤 삭제했습니다.

배운 점

  • 보안 판단은 라우터가 내린 결정에 붙입니다. 경로 문자열을 다시 해석하면 라우터와 다른 결론을 낼 수 있습니다.
  • "꺼져 있다"는 방어가 아닙니다. 꺼진 기능의 코드도 설정이 비었을 때 거부해야 합니다(fail-closed).
  • 재현이 먼저입니다. 수정 전 커밋을 빌드해 실제로 뚫리는지 확인한 덕분에 심각도를 확신할 수 있었습니다.
  • 정책은 새 입력에만 적용합니다. 비밀번호 최소 길이·72바이트 제한을 로그인에도 걸면 기존 사용자가 잠깁니다.

자료: 보안 감사, API 보안 학습 가이드, DB 개선 가이드, DB 가이드 8.4

#8단계: 학습 문서와 docs/html 학습 사이트

요청: 전체 작업 내역과 알아야 할 내용을 docs/html/ 아래 웹사이트 구조의 학습 자료로 만들고, 사이트 자체도 문서화해 계속 갱신할 수 있게 합니다.

결정(사용자)

  • 평소에는 md만 수정하고, 필요한 시점에 현재 md 전체를 기준으로 HTML을 독립적으로 구성합니다.
  • 사이트 관련 트리(생성기, 설정, 문서, 결과)는 모두 docs/html/ 아래에 둡니다.

조치

구분 내용
새 학습 문서 API 보안 학습 가이드, DB 개선 가이드, 용어집, 보안 감사 리포트
생성기 docs/html/_tools/build.mjs: md → HTML, GitHub 방식 앵커, 링크 재작성(코드 파일은 스냅샷 커밋의 GitHub 링크), 깨진 링크·앵커면 실패
사이트 기능 학습 순서 사이드바, 검색(file://에서도 동작), 목차, 이전/다음, 다크 테마, 읽음 표시와 진도
명령 docs:html(스냅샷), docs:html:verify(검사만, CI), docs:html:status(바뀐 md 목록)
문서화 사이트 관리 가이드: 구조, 갱신 시점과 절차, 링크 규칙, 문제 해결, 체크리스트

배운 점

  • 원본은 하나만 둡니다. 같은 내용을 md와 HTML 두 벌로 관리하면 반드시 어긋납니다. HTML은 원본에서 만든 결과물로 취급합니다.
  • 문서 링크도 테스트 대상입니다. 생성기가 모든 내부 링크와 앵커를 검사하므로, 제목을 바꾸면 그 제목을 가리키던 링크를 바로 알 수 있습니다.
  • 갱신 시점과 무결성 검사를 분리합니다. 스냅샷은 사람이 정한 시점에 만들고, 링크 검사는 매 PR 자동으로 합니다.

자료: 사이트 관리 가이드, 학습 로드맵

#반복해서 쓰인 원칙

원칙 이번 작업에서의 예
같은 규칙은 한 곳에 env 파일 선택(env-files.ts), 환경변수 키 목록(runtime-env-keys.cjs), APP_TABLES
목록이 어긋나지 않게 spec으로 고정 런타임 키 drift spec, APP_TABLES 대조 spec, 쓰기 범위 spec
fail fast: 시작 전에 막기 기동 시 설정 검증, env:check, 권한·소유 사전 점검
읽기 전용 점검이 먼저 db:check, migration:show, 운영 배포 전 db:check:prod
최소 권한 앱 DB 단위 GRANT, 운영 계정 '<app>'@'localhost', 운영에서 DB 생성 금지
위험한 기능은 명시적으로 켜기 SNS opt-in, Naver accessToken 기본 차단, synchronize 금지
설정이 비면 거부(fail-closed) audience·KAKAO_APP_ID·redirect 허용 목록이 비면 503 CONFIG_MISSING
보안 판단은 메타데이터로 @AdminOnly, @SocialProviderRoute. 경로 문자열로 판단하지 않음
원본은 하나, 결과물은 생성 md → HTML 스냅샷, runtime-env-keys.cjs → PM2·Secrets export
빈 DB에서 처음부터 검증 CI database job, db:reset:test
비밀은 출력하지 않기 비밀번호·secret 미출력, SHOW GRANTS 해시 가림, Hint는 키 존재만
사람이 결정할 것은 기록하고 남기기 DB-12 drift 방향, P0 배포 전 확인 항목(감사 리포트 6장)
